# Pipeline review — implementation, logic rationale, weaknesses, maturity

**Scope.** A code-first audit of this repository: the pipeline as *implemented* (not as documented),
the rationale behind each design choice, the defects and structural weaknesses, and a maturity
assessment per engine. Written with the planned extensions in view: coupling to the MicroGridsPy
long-term planning model through an iterative LCOE loop, and adding an on-grid (unreliable main
grid, outages, tariffs) option.

**Evidence base.** Static read of all of `core/`, `pages/`, `scripts/`, `tests/` and `docs/`, plus
an executed run of the Mafa case study (240 customers) and the full test suite on
pandapower 3.5.6 / geopandas 1.2.0 / numpy 2.4.6. Numbers quoted as "measured" come from that run.

---

## 1. The pipeline as implemented

Entry point `core/workflow/mvp_runner.py::run_simplified_mvp`. Deterministic, sequential, no solver.

```
1  load_inputs + input_schemas          clean, coerce, default-fill, hard-stop validation
2  customers_to_engine_gdf              lat/lon -> local UTM, MVP schema -> legacy engine schema
3  build_lv_topology                    road-sampled poles -> greedy association -> complete-graph MST
                                        -> span densification   [the ONE shared geometry call]
   |
   +-- A  _run_full_lv                  flat LV, size_conductors loop, 3 PF snapshots, cost
   |     |
   |     +-- C  _run_mvlv(A.grid_ids)   partition_zones -> per-zone LV trees + sizing -> MST MV trunk
   |     |                               -> explicit step-up -> MV rank sweep -> PF
   |     |     +-- D  per-zone terminal-subtree SHS screen -> re-partition + rebuild MV/LV
   |     |
   |     +-- B  LV terminal-subtree SHS screen -> rebuild flat LV on remainder
   |
4  service obligations                  must_connect violations force infeasible
5  recommendation                       argmin total_npc among feasible
```

Three orthogonal engines, each a geometric heuristic with a power-flow check bolted on afterwards:

| | Engine 1 — LV topology | Engine 2 — MV/transformers | Engine 3 — SHS screen |
|---|---|---|---|
| Unit | poles, drops, radial MST | zones, transformers, MV MST | terminal subtrees (leaf branches) |
| Objective | min (penalised) length | min `k` holding the voltage cap | `NPC_SHS < avoided grid cost` |
| Electrical role | reconductoring repairs ΔV/loading | 11 kV evacuation to derated DTs | carve off branches cheaper off-grid |

### Logic rationale (why it is built this way)

The architecture is a deliberate **decoupling of geometry from electrics**. Topology is generated by
length-minimising heuristics (MST, greedy association, k-means/linkage zoning) and then *repaired*
reactively by a conductor-rank loop until the power flow passes. This buys tractability: four
architectures × (present, horizon, stress) snapshots × many settlements, with no MILP and no solver
licence. The cost is that every electrical result is "a geometry that survived a power-flow check",
not a geometry chosen to optimise the electrics — `docs/METHODOLOGY_ENGINES.md` states this honestly
and it is the correct framing.

Three further choices are worth naming because the extensions depend on them:

1. **The SHS decision unit is the terminal subtree**, enumerated from the rooted tree's forks. This is
   a genuinely good idea: it is threshold-free, forms a laminar family (so a greedy claimed-set
   resolves nesting without double counting), and excludes the un-cuttable trunk by construction.
2. **Feasibility is gated on one snapshot** (horizon, diversified at `cf=0.6`); the coincident-peak
   snapshot (`cf=1.0`) is computed but explicitly non-gating.
3. **Generation is priced by a single flat LCOE** on grid-served energy, so grid and SHS are costed on
   the same footing. This is the designated seam for MicroGridsPy — and, as §3.1 shows, it has become
   the dominant term in every result.

## 2. Documentation state: the three docs disagree with the code

`METHODOLOGY_ENGINES.md` (newest, commit `4430a40`) matches the code. `MODEL_REFERENCE.md` and
`WORKFLOW.md` describe the **pre-`a58778e` model** and are now wrong on load-bearing points:

| Topic | `MODEL_REFERENCE.md` / `WORKFLOW.md` say | Code does |
|---|---|---|
| MV source | slack at fixed **1.04 pu on the MV bus**, no step-up | single slack on plant LV bus at `source_vm_pu` (default **1.0**) + **explicit step-up transformer** (`pandapower_builder.py:160-185`) |
| Zoning | greedy farthest-first (`capacity`), `k` a byproduct | default `clustering_criterion = "voltage_cap"`: k-means + PF-driven k search (`mvp_runner.py:338-384`) |
| Avoided cost, Case D | omits avoided generation | credits avoided generation in **both** screens (`mvp_runner.py:150`) |
| Governing zone params | `max_lv_zone_radius_m`, `max_zone_customers` bound every zone | **ignored** under `voltage_cap` and `distance_cap`; only `capacity` reads them |

`CASE_STUDY_COMPARISON.md` carries a correct self-invalidating banner, but its headline result
(**16 SHS units, 6.7 % coverage** at Mafa) is off by an order of magnitude against the current code:
the measured run gives **136 SHS units, 57 %**. The narrative conclusions ("no branch is remote enough
for SHS", "dispersion creates the SHS opportunity") no longer describe the model's behaviour.

Also stale: `examples/*/cost_parameters.csv` still carry four retired keys
(`dmax_lv_service_zone_m`, `lmax_lv_path_m`, `remote_branch_length_threshold_m`,
`loss_threshold_percent`), and **no bundled dataset sets `generation_lcoe_per_kwh` or
`coincidence_factor`** — every published result rests on the hard-coded defaults 0.25 €/kWh and 0.6.

## 3. Core weaknesses

### 3.1 The flat generation LCOE has silently become the model (methodological, critical)

Measured Mafa NPC composition:

| Candidate | generation | losses | SHS | grid capex | total |
|---|---|---|---|---|---|
| A Full LV (infeasible) | **84.7 %** | 0.0 % | — | 15.3 % | 1.193 M |
| B LV+SHS (infeasible) | **74.3 %** | 0.0 % | 17.6 % | 8.1 % | 1.138 M |
| C MV/LV | **71.1 %** | 5.9 % | — | 23.0 % | 1.422 M |
| D MV/LV+SHS | **63.3 %** | 5.4 % | 15.5 % | 15.8 % | 1.314 M |

Two consequences follow, and they pull in opposite directions:

- **Between network architectures the term is inert.** `generation_npc` depends only on *which
  customers* are grid-served, not on how they are wired: A and C are identical to the euro
  (1,010,989). So 71–85 % of the objective cannot distinguish LV from MV/LV. The architecture
  choice is actually decided by the 15–29 % tail, while the headline NPC is dominated by an
  uncalibrated scalar.
- **Between grid and SHS the term is decisive.** Avoided generation PV for one Mafa household is
  400 kWh × 0.25 × AF(0.10,15) = **761 €** (1,711 € at 900 kWh, 3,423 € at 1,800 kWh), against an
  SHS_T3 package NPC of **1,329 €**. Adding avoided connection+metering (180 €) means any eligible
  branch of ≳900 kWh households clears the gate on the generation credit **alone**, before a single
  metre of avoided line is counted.

The result is a degenerate screen: in the measured run **every single candidate branch was
selected — 17/17 in Case B, 23/23 in Case D**, zero rejections. A screen that never says no is not
screening; it is applying a uniform policy whose single free parameter is the LCOE. The docs'
`METHODOLOGY_ENGINES.md` §3.6 Q2 anticipates this ("selects more SHS") but underestimates it
(14 → 26 on the small example; the real-case effect is 16 → 136).

**This is exactly the gap the MicroGridsPy coupling must close**, and it also means the current
results are not a defensible baseline to iterate from. See §5.

> *Update.* The synthetic-curve experiment ([`CONVERGENCE_EXPERIMENT.md`](CONVERGENCE_EXPERIMENT.md))
> shows a scale-economy curve alone does **not** undo this on Mafa at 0.25 €/kWh: the price *level*
> against the SHS cost per kWh (and SHS package eligibility) decides it. The coupling is still
> needed to get the price right, but a service-quality term and the package catalogue matter as much.

### 3.2 Non-convergence is rewarded with zero loss cost (correctness defect, high)

`validation.py` returns `losses_kw = NaN` when the power flow diverges; `cost_model.py:69-75`
NaN-guards that to **0.0**. So a diverged candidate pays no loss cost at all. Measured: A and B
show `loss_pv_cost = 0`, while C and D pay 83.5 k and 71.6 k on the same settlement. B therefore
reports 1.138 M — **cheaper than the recommended, feasible D at 1.314 M** — purely because its power
flow collapsed.

That is harmless while a feasible candidate exists, but `mvp_runner.py:837` falls back to
`argmin total_npc` over *all* candidates when none is feasible, i.e. the "least-infeasible"
recommendation is systematically biased toward the **most** broken candidate. The four-way comparison
table also puts these numbers side by side with no indication that two of them are missing a cost
component. Fix: carry losses as `NaN` into the breakdown and exclude/flag the component, or rank
infeasible candidates by severity of violation rather than by NPC.

### 3.3 `PFOutcome.converged` is dead; a silent non-convergence reads as feasible (correctness, medium)

`validation.py:36` computes `converged = bool(net.converged)` and never uses it; line 79 hard-codes
`converged=True`. Today pandapower raises `LoadflowNotConverged`, so the `except` branch catches it.
But if `runpp` ever returns non-converged without raising (changed default, `init` fallback, a future
API), every limit check is a comparison against NaN → all `False` → `feasible = True` and
`bottleneck = "within limits"`. A one-line fix (`if not converged: return ...`) removes a silent
false-pass on the only safety gate in the model.

### 3.4 The `voltage_cap` k-search is not minimal, and is not monotone (methodological, high)

The docs claim `voltage_cap` "backtracks to **guarantee** minimality". The measured search history
disproves the premise:

```
C: k=2 diverged | k=3 diverged | k=4 diverged | k=5 ΔV 0.1234 | k=6 ΔV 0.1048 | k=7 ΔV 0.0868 OK
D: k=1 diverged | k=2 diverged | k=3 ΔV 0.1004 | k=4 ΔV 0.1028 | k=5 ΔV 0.0865 OK
```

Case D's k=4 is **worse** than k=3 (0.1028 vs 0.1004 pu drop). Feasibility is not monotone in `k`
because k-means re-partitions from scratch at each `k`, so clusters are not nested — more
transformers can mean worse voltage. The backtrack loop `break`s on the first infeasible `k`
(`mvp_runner.py:361-371`), so it is a local, not a global, minimum; and because the seed diverged in
both cases the backtrack branch never executed at all. Also note D's k=3 at exactly 0.900 pu was
rejected — a floating-point knife edge on the limit.

Two further problems with "minimum `k`" as the criterion:

- **It deliberately burns all the voltage headroom.** Measured design min voltage: 0.913 (C) /
  0.914 (D) against a 0.90 limit — 1.3 pp of margin. Under the coincident-peak snapshot both
  recommended candidates **breach their own limits**: 0.845/0.846 pu and 138 % line loading. Since
  the stress snapshot is non-gating by design, the model recommends a network that is infeasible
  whenever diversity is worse than the assumed `cf = 0.6`. Minimising `k` is a least-robust
  selector, not a least-cost one.
- **No guard on `k` vs customer count.** The climb loop (`mvp_runner.py:373-382`) is bounded only by
  `max_transformers` (default 12) and calls `partition_kmeans` with no `try`. Verified: `k > n`
  raises `ValueError: 9 clusters requested but only 6 customers`, and coincident coordinates raise
  `k-means failed to produce 3 non-empty clusters`. Either crashes the whole run for a small or
  duplicate-coordinate settlement.

### 3.5 Transformers are systematically oversized by ~2×, charged only to C/D (methodological, high)

Zones are sized on the **coincident** horizon peak (`cf = 1.0`) and validated at `cf = 0.6`, with a
1.2 safety factor in `select_transformer` and a further 1.2 derating divisor on the zone kVA cap
(`mvp_runner.py:397`). Net oversizing relative to the snapshot actually simulated is
`1/0.6 × 1.2 = 2.0×`. Measured consequence: design transformer loading **50 % (C) / 47 % (D)** — so
`max_transformer_loading_percent` can never bind at the design snapshot, and transformer capex
(138.7 k / 110.5 k, the largest grid-capex item) is roughly double what the design case requires.

Compounding this, the new explicit step-up is sized on the whole settlement's coincident S × 1.2 and
its capex is added to `transformer_cost` — while the flat-LV cases A/B get an **ideal, free, infinite-
stiffness 0.4 kV slack at 1.0 pu** with no plant transformer, no impedance and no iron losses
(`pandapower_builder.py:97`). The step-up was added to make C/D honest; the asymmetry now biases the
LV-vs-MV/LV comparison toward LV in exactly the compact cases where A/B are feasible and the
comparison matters.

Related: `build_lv_net` hard-codes `vm_pu=1.0` and ignores `source_vm_pu`, so changing the sending
voltage in the UI silently moves C/D only.

### 3.6 The avoided-cost model and the NPC model are not the same model (methodological, medium)

The SHS gate (`_avoided_grid_cost`, `mvp_runner.py:135-157`) and `total_npc`
(`cost_model.CostBreakdown`) are inconsistent in three ways:

- **Service drops are credited but never charged.** `mvp_runner.py:147` prices
  `service_drop_m × cheapest_LV_cost_per_m × civil_multiplier` as avoided, but no candidate's
  `lv_line_cost` includes service drops (only `topology.edges_4326`). The gate credits a cost the
  objective does not carry.
- **Growth is applied inconsistently.** `generation_present_value` uses `annual_kwh_now` held flat
  (`cost_model.py:54-66`) while `loss_present_value` levelises the **horizon** loss snapshot flat
  (`cost_model.py:69-75`). Energy is costed at year 0 and losses at year T, in the same sum.
- **Delivered ≠ generated.** The LCOE is applied to delivered energy only; grid losses are priced
  separately at `loss_value_per_kwh` (0.20–0.25) rather than at the generation LCOE (0.25). Grid
  generation is therefore undercounted by the loss fraction.

Beyond consistency, the estimates are **marginal on the pre-removal network** while the realised
candidate is a **full rebuild**. For Case D this is severe: the screen runs on Case C's zone trees,
then D **re-partitions from scratch** (7 zones → 5 measured, with a fresh k-search), so the
branch/pole/loss credits that drove the decision refer to a geometry that no longer exists.

### 3.7 SHS eligibility is a knife edge on a discrete catalogue (methodological, medium)

The median Mafa household (0.25 kW, tier 2, g=0.04, T=15) has horizon peak
`0.25 × 1.04^15 = 0.45024 kW` against `SHS_T2.max_peak_kw = 0.45`. It misses by **0.05 %** and is
pushed to `SHS_T3`, whose NPC is **1,329 € vs 823 €** — a 61 % cost jump from a rounding-scale
margin. Measured package mix in the recommended case: 122 × SHS_T3, 14 × SHS_T4, **zero** T1/T2.
With all-or-nothing subtree eligibility, one such customer also vetoes an entire branch. Needs a
tolerance, a de-rating convention, or continuous sizing.

Also: `npc.py:27` defaults `replacement_fraction` to **0.6** while `input_schemas.py` fills **0.8** —
divergent defaults for the same quantity, masked only because the schema always fills it.

### 3.8 Case C and D inherit Case A's unserved set (structural, medium)

`_run_mvlv` is called with `full_res.grid_customer_ids` — the customers the **flat-LV** topology run
managed to associate to a pole. Any customer the flat-LV engine drops can therefore never be served
by MV/LV, however well a local transformer zone would reach it. The MV/LV architectures are
penalised by a limitation of a different architecture's geometry run. (Not visible at Mafa —
0 service-tier violations — but structurally wrong and will bite on sparse-road settlements.)

### 3.9 Engineering hygiene and reproducibility (medium)

- **21 editor swap files are committed** (`*.py.tmp.<pid>.<hash>` across `core/workflow/`,
  `core/topology/`, `core/viz/`, `core/io/`, `core/electrical/`) along with every `__pycache__/*.pyc`.
  There is **no `.gitignore`**. `mvp_runner.py.tmp.*` alone has 8 near-duplicate copies of the
  orchestrator — a real hazard for anyone grepping or bisecting.
- **No dependency pinning.** `environment.yml` lists bare package names with no versions; `altair` is
  imported directly by `core/viz/charts.py:12` but **not declared** (it works only as a streamlit
  transitive). No `pyproject.toml`, no lockfile, no CI, no `LICENSE` file despite the README's EUPL
  claim.
- `unary_union` is used at 5 sites in the legacy engine (`distribution_io.py:47`,
  `distribution_algos.py:845`, `distribution_service.py:869,1184,1187`) and emits deprecation
  warnings on geopandas ≥1.0, while `mvlv_service_zones.py` already uses `union_all()`. Removal is
  scheduled upstream.
- `normalize_cost_parameters` **silently drops unknown keys** (`if key not in out: continue`), so a
  typo in a cost CSV is accepted and ignored rather than reported.
- Dead code: `zone_apparent_power_kva` computes `kva = _customer_kva(...)` (line 56) and never uses it.
- **Scalability.** `create_graph_and_mst` builds a dense complete graph with per-edge shapely
  construction ("OK for a few hundred"), and in `road_attracted` mode samples every candidate edge at
  10 m. The `voltage_cap` search multiplies this: the measured Mafa run executed **11 full MV/LV
  builds** (6 for C, 5 for D), each with per-zone sizing loops and an MV rank sweep — **138 s for 240
  customers**. The 521-customer `complete` dataset will be minutes-to-tens-of-minutes, and that is
  one deterministic run with no scenarios.

### 3.10 Testing (medium)

52 tests, all green (22 s). But the suite is almost entirely **structural**: "four candidates
present", "exactly one slack", "ids are namespaced", "table covers every customer". There is no
numerical ground truth anywhere — no hand-calculated two-bus voltage drop, no golden-value NPC
regression, no monotonicity check on `size_conductors`, no test that would have caught §3.2 (zero
loss cost on divergence), §3.3 (dead `converged`), §3.4 (non-monotone k), or §3.6 (credit/charge
asymmetry). Every integration test runs on the 60-customer synthetic example only; the real case
studies are exercised by unasserted smoke scripts. `tests/conftest.py` still passes the retired
`dmax_lv_service_zone_m` / `lmax_lv_path_m` keys.

## 4. Maturity assessment

| Component | Maturity | Reading |
|---|---|---|
| Input schemas, defaulting, validation | **Solid** | Explicit contract, hard stops on real errors, sensible defaults. Only gap: silent unknown-key drop. |
| Engine 1 — LV topology | **Mature as a heuristic** | Inherited, well-understood, documented limits (length-MST ≠ min-loss, impedance-free drops, balanced 3-φ). Scalability is the binding constraint. |
| Engine 2 — MV/transformers | **Immature / in flux** | Rewritten one commit ago. The step-up fix is a genuine improvement, but the k-criterion is unsound (§3.4), sizing is ~2× conservative (§3.5), and two of its three criteria ignore the zone parameters the docs advertise. |
| Engine 3 — SHS screen | **Good skeleton, broken calibration** | Terminal-subtree enumeration + laminar greedy is the strongest idea in the repo. The economic gate it feeds is currently degenerate (100 % acceptance, §3.1). |
| Power-flow validation | **Thin** | One function, one snapshot, four limits. Two defects on the only safety gate (§3.2, §3.3). No unbalance, no reliability, no time series. |
| Economics / NPC | **Internally inconsistent** | §3.1, §3.2, §3.6, §3.7. The dominant term is an uncalibrated scalar. |
| Orchestration & traceability | **Strong** | Honest `decision_log`, per-candidate artefacts, three snapshots stored, deterministic seeds. This is the part that makes the rest auditable. |
| UI / exports / viz | **Good** | Comprehensive, readable, parameter-exposed, zip exports. |
| Docs | **Divergent** | One doc current, two describing a retired model, one case study off by 8× on its headline. |
| Repo engineering | **Pre-alpha** | No `.gitignore`, no pins, no CI, no LICENSE, 21 swap files and all `.pyc` committed. |

**Overall.** This is a credible, well-traced research prototype with one genuinely novel component
(threshold-free terminal-subtree SHS screening) and an honest self-description of its own
simplifications. It is **not yet a stable baseline**: the objective function is dominated by an
uncalibrated parameter, the headline documented result is an order of magnitude from what the code
now produces, the feasibility gate has two correctness defects, and the MV zoning criterion rests on
a monotonicity assumption its own logs refute. Call it a working diagnostic at the end of its first
iteration, not a model ready to be coupled to.

## 5. Implications for the planned extensions

### 5.1 MicroGridsPy coupling / iterative LCOE loop

This is the right next step and it lands on the right seam — but the current state makes three
things necessary first.

1. **The loop will be unstable as specified.** `generation_npc` is 63–85 % of the objective, and the
   SHS gate's dominant term is avoided generation. An iteration `LCOE → demand → connection/SHS
   choice → served energy & load shape → LCOE` therefore has a strong positive feedback: SHS removal
   cuts served energy, a flat LCOE does not fall with scale, so the next pass removes more. Today's
   100 % branch-acceptance rate (§3.1) is that feedback already at its fixed point with a frozen
   LCOE. The loop needs: (a) an LCOE that genuinely **scales with served energy and load shape**,
   (b) a convergence criterion plus a cycle detector, and (c) optionally a damped update.
   *Measured since* ([`CONVERGENCE_EXPERIMENT.md`](CONVERGENCE_EXPERIMENT.md)): on Mafa the plain
   undamped loop converges in 2–3 rounds for every synthetic curve and price tested, with no
   oscillation; damping only slows it. Scale economies create both a restoring and an opposing force,
   and the restoring one wins. The earlier "expect oscillation" warning did not hold.
2. **Fix the marginal-vs-realised gap before iterating** (§3.6), because the loop multiplies it. With
   generation credited exactly, the gate is in principle the true total-NPC break-even; a
   re-solve-after-each-cut (commit only if realised NPC drops) or an ILP over the laminar subtree
   family would make each outer iteration actually monotone in NPC. Without it, the outer loop is
   iterating on an objective the inner screen does not optimise.
3. **The data interface already half-exists but is unused.** `examples/nga_1/Aggregated Demand.csv`
   is an 8760-hour MicroGridsPy-shaped aggregated demand series (semicolon/comma-decimal, single
   year), and `examples/mafa case study/category_profiles.csv` holds 8760-hour profiles for 12
   categories. **Nothing in `core/` reads either** — `scripts/build_mafa_example.py` collapses them
   offline to `(peak_kw, annual_kwh)` scalars and the pipeline consumes only those two numbers. The
   coupling work is therefore: promote profiles to first-class inputs, derive the coincidence factor
   as an *emergent* property of aggregation instead of the flat 0.6, and feed MicroGridsPy the
   spatially-aggregated served load shape rather than an annual total. That also removes §3.5's
   sizing/validation `cf` mismatch at its root.

One design note on the coupling boundary: the model's spatial aggregation of demand (single
injection point, pole-lumped loads, one coincidence factor) is fine for a planning comparison, but
the quantity you hand MicroGridsPy must be **generated** energy, not delivered. Grid losses are
currently outside the LCOE basis (§3.6) and would otherwise be charged twice at two different
prices.

### 5.2 Adding the on-grid option (unreliable grid, outages, tariffs)

Three structural prerequisites, in order:

1. **A reliability dimension does not exist anywhere in the model.** Everything is a deterministic
   peak snapshot; there is no LOLP, no expected unserved energy, no autonomy. An unreliable main
   grid is *defined* by its outage statistics, so the comparison currently has no axis on which to
   place it. Without one, an on-grid option with cheap tariffs and 8 h/day availability will simply
   win on NPC. This is also already a fairness gap in the existing comparison: a grid connection and
   an SHS package are compared on cost with no service-quality term (`METHODOLOGY_ENGINES.md` §3.6
   Q3 flags it).
2. **Tariffs need an energy-cost abstraction that LCOE currently monopolises.** Today grid energy has
   exactly one price (`generation_lcoe_per_kwh`) applied to one basis (`annual_kwh_now`, flat). An
   on-grid case needs a per-architecture, time-varying energy cost (tariff when the grid is up,
   backup generation or unserved energy when it is not), plus a one-off interconnection/MV-extension
   capex to the nearest grid node. That is a refactor of `cost_model.py` into a per-candidate energy
   cost model, not a new parameter — and it is the same refactor §5.1 needs.
3. **A fifth and sixth candidate break the hard-coded A/B/C/D structure.** `run_simplified_mvp`
   enumerates four cases by hand, with `_run_mvlv` shared between C and D and the SHS screens
   duplicated per track. Adding on-grid (and on-grid + SHS, and grid-connected-with-backup) means
   promoting candidates to a registry — a `build(ctx, grid_ids) -> CaseResult` contract — before the
   combinatorics multiply. Doing it now is cheap; doing it after two more hand-written cases is not.

### 5.3 Suggested order of work

1. §3.2 and §3.3 — two small fixes to the feasibility/costing gate; they are cheap and they
   invalidate results until done.
2. §3.9 — `.gitignore`, delete the 21 swap files, pin dependencies, declare `altair`, add CI running
   the existing 52 tests. One afternoon; makes everything after it reproducible.
3. Re-run the case studies and rewrite `MODEL_REFERENCE.md`, `WORKFLOW.md` and
   `CASE_STUDY_COMPARISON.md` against the current code (§2). The 16 → 136 SHS shift is a finding in
   its own right and deserves to be reported, not buried.
4. §3.4 and §3.5 — replace "minimum k" with a criterion that keeps voltage margin (or gate on the
   coincident snapshot), and reconcile the sizing/validation coincidence factors.
5. §3.6 and §3.7 — unify the avoided-cost and NPC models; add package-sizing tolerance.
6. Then profiles → emergent diversity → MicroGridsPy loop (§5.1), with the energy-cost refactor
   shared with the on-grid work (§5.2).

Steps 1–3 are prerequisites for trusting any number the model currently prints; 4–5 are
prerequisites for the coupling loop converging to something meaningful.
